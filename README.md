# SEVPN

Kotlin Android client for the **native SoftEther protocol**, using Android
VpnService and a user-space Ethernet/ARP/DHCP endpoint. No root, Linux TAP,
vpnclient executable, MVPN, server patches or trust-all TLS manager.

This is a working implementation to validate, **not a production-certified
release**. Automated core tests and APK builds are recorded in TEST_RESULTS.md.
Real phone/stock-server end-to-end acceptance remains pending; see
[the acceptance matrix](integration/ACCEPTANCE.md). Do not infer working
Android Internet routing from compilation or host unit tests alone.

## Build

Open the project root in Android Studio. The supplied environment has
Android SDK **37.0**, AGP **9.4.1**, Gradle **9.6.0** and JBR **25**; these are
the configured versions. minSdk is **26**, targetSdk is **37**. Core JVM
modules use a Java 17 toolchain/bytecode, provisioned by Gradle. No NDK needed.
Select Android Studio's JBR as the Gradle JDK. Initial sync needs Google
Maven, Maven Central, Gradle distributions and JVM toolchain download access.

On Windows PowerShell:

```powershell
$env:JAVA_HOME = 'C:\Program Files\Android\Android Studio\jbr'
.\gradlew.bat test :app:assembleDebug :app:assembleDebugAndroidTest :integration:installDist
.\tools\package-apk.ps1
```

On macOS/Linux, configure a suitable JDK and SDK (`ANDROID_HOME` or
`local.properties`), then use `./gradlew` with the same tasks. Debug output:
`app/build/outputs/apk/debug/app-debug.apk`; packaged phone test artifact:
`dist/SEVPN-0.1.1-debug.apk` plus `dist/SHA256SUMS.txt`.

```powershell
adb install -r .\dist\SEVPN-0.1.1-debug.apk
```

Without USB debugging, transfer the APK to your phone and allow installation
from that source. The debug signature is for development; release signing
and store publication are separate work.

Also run `./gradlew :app:lintDebug` when the lint tool is available from Google
Maven. In the supplied build environment, its official Maven URLs returned
404 for `com.android.tools.lint:lint-gradle:32.4.1`; lint could not execute.
This is recorded as an open check in TEST_RESULTS.md, not a lint pass.

## Connect on your phone

1. Enter profile name, server hostname/IP, port, Virtual Hub, username and
   password. The server must support SoftEther native TCP/TLS on this port.
2. Use normal CA trust with the certificate's matching hostname. For a private
   or self-signed certificate, enter its **SHA-256 leaf certificate fingerprint**
   in advanced settings, obtained from your administrator through a trusted
   channel. Pin mode is explicitly labeled and checks certificate validity.
3. The hub needs DHCP, an IPv4 Internet gateway and usable DNS. Stock SecureNAT
   can provide these; a bridged LAN DHCP/router can also provide them.
4. Tap Connect and approve Android's VPN consent dialog. Notification permission
   is requested separately; declining it does not bypass VPN consent.
5. Wait through authentication, DHCP and Android TUN configuration. Connected
   means the session, lease, TUN and forwarding workers are established.
6. Open an IPv4 website and check that its reported egress address belongs to
   your VPN server. Verify DNS and confirm the real hub session server-side.
7. Disconnect; the VPN indicator and notification should disappear. Reconnect
   and test Wi-Fi/mobile changes and Android's VPN revocation.

To calculate a fingerprint from the administrator's certificate file:

```sh
openssl x509 -in server.crt -noout -fingerprint -sha256
```

Passwords are encrypted with an Android Keystore AES-GCM key. The UI does not
reload them as plaintext, excludes them from saved UI state and blocks
screenshots. Leaving password blank keeps a stored password only for the same
server/port/hub/user identity. For a new profile, blank is an explicitly empty
SoftEther password. Profile edits are disabled while a connection is active.

## Tests

`test` covers PACK, SHA-0/authentication, HTTP/native framing, unsafe negotiation,
IPv4/UDP checksums, route selection, Ethernet/ARP, cache expiry, DHCP options,
DORA/renewal, bounded fuzz inputs, real loopback TLS, resource cleanup and
profile validation. Binary hash/PACK fixtures were generated by executing
actual upstream C functions, not a second Kotlin implementation.

To regenerate those fixtures, obtain the exact upstream source:

```sh
git clone --branch v4.44-9807-rtm --depth 1 https://github.com/SoftEtherVPN/SoftEtherVPN_Stable.git
python tools/upstream_vectors.py
```

Requires Python 3 and clang/cc. Upstream source/research checkouts are ignored
by this project's Git repository and are not bundled in the APK.

Device-only tests use platform Instrumentation plus JUnit4:

```powershell
.\gradlew.bat :app:connectedDebugAndroidTest
```

These exercise actual Android Keystore encryption, random IVs, profile AAD
and Android socket descriptor creation before VPN protection.
They require a connected phone/emulator and have not been substituted with
JVM Android mocks. [Integration instructions](integration/README.md) include
a pinned, unmodified Stable Docker server and real IPv4 DNS/TCP probes.

## Diagnostics and limits

Export sanitized diagnostics from the main screen after a failure. Export
contains the app version, local phase names, failure/operation enums, numeric
OS/server errors and byte counters. It excludes raw exception text, passwords,
hashes, keys and packet contents. The last failure stays visible during retries. Screenshots
are intentionally blocked, so use diagnostic export when reporting a failure.

Initial version: IPv4 full tunnel, one protected TCP/TLS connection, password
and anonymous authentication, DHCP and broadcast lease renewal, bounded ARP
queues and reconnect backoff. DHCP subnet prefixes 1–30 and on-link gateways
are supported. Explicit DNS override is optional; there is no silent public
DNS fallback. IPv6 is blocked while TUN is active.

Deferred: UDP acceleration, multi-channel optimization, compression, RC4,
cluster redirects, VPN Azure/NAT-T, certificate authentication, IPv6,
split/per-app tunneling, static IP and always-on startup. No kill switch is
implemented: traffic can use the physical network during initial connection
or reconnection. Use this behavior deliberately during evaluation.
